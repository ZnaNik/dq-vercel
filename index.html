1. Ситуация

Компания — крупный ритейлер, 8 000 сотрудников. В центральное HR-хранилище данные поступают из нескольких систем. Конечные потребители — Payroll (расчёт зарплат каждую ночь), HR BI, Compliance-отчёты в ФНС/ПФР.

Инцидент: Регулятор прислал замечание — задвоенные выплаты у 17 сотрудников, 4 сотрудника без трудовых договоров в отчёте. Финансовые потери ~4,2 млн руб. за полгода. Команда не знает, откуда пришли грязные данные — нет ни одной DQ-проверки, нет мониторинга.

Что сейчас есть — схема AS-IS

CDC-события и API-ответы падают напрямую в хранилище через Kafka, но без слоёв и без проверок качества. Airflow формально запускает пайплайны, но никаких DQ-шагов нет:

Откройте Excalidraw и нарисуйте целевую архитектуру системы контроля качества данных. Схема строится с нуля — никаких заготовок нет.

Интервьюер наблюдает и задаёт вопросы по ходу рисования. Важно не только что нарисовано, но и как кандидат объясняет свои решения.

Опорные вопросы (задаёт интервьюер)

  • Где именно в потоке ты поставишь DQ-проверки? Почему именно там?
  • Что происходит с записью, которая не прошла проверку — CRITICAL vs WARNING?
  • Как Payroll узнаёт, что данные готовы и безопасны для расчёта?
  • Кто отвечает за исправление данных в карантине?
  • Какой инструмент ты поставишь для мониторинга качества и почему?
🔒 Эталон для интервьюера
  • Слои: RAW (всё как пришло из Kafka, иммутабельно) → Staging (очищенное, прошедшее DQ) → Core/DWH (только валидированные данные, готовые к потребителям). Кандидат должен назвать все три слоя и объяснить зачем каждый
  • Оркестрация: Airflow DAG — один таск на каждый шаг: ingest → raw → dq_check → staging → dq_cross → core → payroll_gate. Senior объяснит, что gate перед Payroll блокирует DAG если DQ Score ниже порога
  • Ingestion: Debezium + Kafka для CDC (1С:ЗУП, 1С:ДО), REST-коннектор для HRM SaaS, Airflow batch-оператор для Legacy CSV
  • DQ Engine: dbt tests на RAW → Staging + Soda Core / Great Expectations для профилирования + OpenMetadata как каталог и UI для DQ Score. Senior называет минимум 2 и объясняет зачем оба
  • Паттерн: Write → Audit → Publish. Кандидат называет сам — это маркер Senior vs Middle
  • Карантин: Отдельная схема, таблица dq_errors с причиной + источником + timestamp. Owner — Data Steward, SLA — 4ч CRITICAL / 24ч WARN
  • Мониторинг: DQ Score по измерениям в Grafana / OpenMetadata. Slack для WARN, PagerDuty для CRITICAL. Airflow-gate перед Payroll: если Validity+Uniqueness < 99% — DAG падает и будит инженера
T3 DQ Score — как измерить качество в цифрах? 10 мин

Вы нашли проблемы, нарисовали архитектуру. Теперь вопрос: как операционно понять, что данные достаточно хороши для Payroll?

Предложите подход к измерению качества: какие измерения важнее для HR-домена, как их взвесить и где поставить порог блокировки. Нарисуйте Scorecard в Excalidraw.

🔒 Эталон для интервьюера
  • DQ Score = Σ(вес_i × доля_прошедших_записей_по_измерению_i). Кандидат должен сам прийти к взвешенной формуле
  • Для HR: Validity и Uniqueness — самые тяжёлые (по 20-25%), прямой финансовый риск. Timeliness — наименее критично
  • Порог блокировки Payroll: Validity ≥ 99% AND Uniqueness = 100%. Ниже — Airflow gate падает, уведомление
  • Тренд важнее абсолюта: падение Score 3 дня подряд = алерт, даже если число выше порога
  • Soda или OpenMetadata дают готовый UI для такого Scorecard — Senior должен это знать

🔒 Эталон для интервьюера — критерии зрелого ответа
  • Автоматика: Airflow gate видит CRITICAL → частичный запуск Payroll для 1 913 чистых записей, 40 CRITICAL → Quarantine, алерт уходит автоматически. «Блокируем всё и ждём» — красный флаг
  • Роутинг по severity: CRITICAL записи — в карантин без Payroll; WARN записи — в Core с флагом dq_flag='WARN', Payroll их пропускает до исправления
  • Оповещения: Slack/PagerDuty → Data Engineer + Head of HR + FinDir. Кандидат должен назвать кто получает и в какой очерёдности
  • Incident ticket: Jira/Confluence с RCA — откуда пришли дубли (1С:ЗУП?), почему salary отрицательная
  • Превенция: Data Contract с источником — формализуем ожидаемый формат, чтобы источник знал требования заранее. Это маркер Senior: думает не только о реакции, но и о предотвращении
