Ключевые элементы которые должен назвать сам:

  • RAW → Staging → Core — три слоя, каждый с объяснением зачем
  • Write-Audit-Publish — паттерн. Маркер Senior: называет сам без подсказки

«Зачем нам три слоя — RAW, Staging, Core? Разве нельзя проверять прямо в DWH?»
✅ Хорошо: RAW иммутабелен — можно перечитать, если нашли баг в правилах. Staging — рабочая зона с незавершёнными проверками. Core — только то, чему доверяют потребители.
🚩 Плохо: «Ну, так архитектурно принято» без объяснения зачем каждый слой.
«Какой инструмент поставишь для DQ-проверок и почему именно он?»
✅ Хорошо: dbt tests — легковесно, в коде, версионируется. Soda — декларативные checks, удобен аналитикам. Great Expectations — гибкость. OpenMetadata — каталог + UI. Называет 2+ и объясняет когда что.
🚩 Плохо: называет только один инструмент без trade-off, или называет только «что-то типа Great Expectations» не зная деталей.
«Что такое Data Contract и зачем он нужен здесь?»
✅ Хорошо: формальное соглашение между владельцем источника (1С:ЗУП) и потребителем (DWH) — описывает схему, типы, допустимые значения, SLA поставки. Нарушение → алерт источнику, не только нам.
🚩 Плохо: «Это что-то про контракты с поставщиками?» или полное непонимание концепции.
«Кто такой Data Steward и чем он отличается от Data Engineer?»
✅ Хорошо: Data Steward — бизнес-роль, знает домен, принимает решения о качестве, отвечает за карантин. Data Engineer — строит пайплайны. Разные люди, разные ответственности.
🚩 Плохо: «Это одно и то же» или не знает кто отвечает за карантин.
T3 DQ Score — как измерить и где порог? 15 мин

Вы построили систему. Как операционно ответить на вопрос: «Данные сегодня хорошего качества?» Предложите подход к измерению и нарисуйте Scorecard в Excalidraw.

🔒 Эталон + скрипт

Ожидаемый Scorecard для HR-домена:

ИзмерениеВесПочему такой весПорог блокировки Payroll
Uniqueness25%Дубли emp_id = двойное начисление= 100%
Validity25%salary < 0, неверный формат счёта = прямые потери≥ 99%
Completeness20%Пустое ФИО = невозможно идентифицировать≥ 98%
Consistency20%Referential integrity = сирота в отчёте регулятора≥ 99%
Accuracy10%Будущая дата, неверный отдел — важно, но не критично≥ 95%

Формула: DQ Score = Σ(вес_i × доля_прошедших_i). Payroll gate блокируется если Uniqueness < 100% ИЛИ Validity < 99%.

Тренд важнее числа: Score 98% три дня подряд и падает → алерт, даже если выше порога.

Инструмент: OpenMetadata или Soda Cloud дают готовый Scorecard UI — Senior должен это знать и предложить.

«Почему Timeliness не включил в Scorecard?»
✅ Хорошо: для HR-домена данные поступают батчами по расписанию, задержка редка и контролируется Airflow. Если бы был real-time домен — добавил бы.
🚩 Плохо: «Забыл» или «Ну там SLA и так есть».

🔒 Эталон + скрипт
✅ Зрелый ответ: частичный запуск Payroll для 1 913 чистых записей. 40 CRITICAL → Quarantine, 47 WARN → Core с dq_flag='WARN'. Алерты автоматически. Incident ticket с RCA.
🚩 Красный флаг: «Стопим Payroll полностью и ждём исправления» — это потеря бизнеса, 1 913 человека не получат зарплату вовремя.

Полный ожидаемый сценарий:

  1. Airflow gate: Uniqueness < 100% → gate не блокирует весь Payroll, а исключает проблемные записи
  2. 40 CRITICAL → Quarantine автоматически + Slack/PagerDuty → Data Engineer + Head of HR + FinDir (в этом порядке)
  3. 47 WARN → Core с флагом, Payroll пропускает, BI видит метку
  4. 1 913 чистых → Payroll запускается штатно
  5. Утром: Jira-тикет с RCA. Откуда дубли? Почему salary отрицательная? Кто owner в 1С:ЗУП?
  6. Долгосрочно: Data Contract с 1С:ЗУП — фиксируем что salary > 0, emp_id уникален, формат паспорта
«Кто должен принять решение — запускать ли Payroll частично — в 02:00 ночи?»
✅ Хорошо: решение должно быть закодировано в правилах системы заранее, не требовать звонка ночью. Senior думает о том чтобы убрать человека из критического пути.
🚩 Плохо: «Звоним Head of HR» — это значит система не настроена, каждый инцидент будит людей.
«Как вы предотвратите повторение этого инцидента?»
✅ Хорошо: Data Contract с источником, OpenMetadata для документирования ожиданий, мониторинг тренда Score (не только абсолютное значение), retro с командой источника.
🚩 Плохо: «Добавим ещё одну проверку» без системного мышления о prevention vs reaction.
